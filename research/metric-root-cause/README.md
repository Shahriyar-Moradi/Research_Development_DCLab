# Why a number changed: metric decomposition and root cause

**Status:** active
**Owner:** DCLab R&D · **Started:** 2026-10-19

## Research question

When a business number moves (a brand's sales down in one mall against last year), which factor moved it, where, and by
how much, answered from approved definitions and tested queries rather than free text-to-SQL, and refused where the data
cannot answer? The answer decides how DCLab's metric_change kind (30.20) reads a why question: which template, which
decomposition, and when it says it cannot tell.

## Why it matters for DCLab

It is the owner's pattern 6 (ask-your-data BI and root-cause analysis). The kind runs as a library
(`dclab_rnd/kinds/metric_change.py`, the library `dclab_core/metric_change.py`): a semantic layer, four tested templates
run as bound SQL on SQLite, the change decomposed in logs (sales = footfall x conversion x basket) with intervals over days,
drill-down by mix against rate, coverage checks, refusals, and a model that only chooses a template and fills it.

## Prediction contract

Not a prediction: an explanation of a change already seen. Written before any answer was scored:

| Item | Value |
|---|---|
| Unit | one question about one metric, its filters, a period and a comparison period |
| Moment | after both periods are over and their rows are in the tables |
| Target | the factor that moved the metric (ranked first), the segment where it moved, or a refusal with what is missing |
| Allowed information | the tables the semantic layer approves, their columns as the layer defines them |
| Forbidden information | anything the layer does not hold (a competitor, a cost): refused, never stretched; free SQL |
| Primary metric | planted causes found and ranked first on the mall sales replica's seeds; a factor moves only when its interval over days, one for all the factors searched (Bonferroni, 90%), excludes zero |

## Result schema

Write results in the shape the rest of the repository already understands, so `dclab_rnd.evidence_index` can index them and the SFT builder can learn from them:

```json
{
  "schema_version": 1,
  "campaign_id": "metric_root_cause_v1",
  "experiment_id": "MCH-001",
  "dataset": "dataset_key",
  "kind": "data_understanding | leakage_audit | feature_engineering | model_selection | optimization_reliability",
  "task_type": "binary | multiclass | regression | timeseries_regression | graph_node_classification | ...",
  "primary_metric": "roc_auc | average_precision | macro_f1 | mae | ...",
  "question": "...",
  "hypothesis": "...",
  "setup_summary": "1-3 sentences: exactly what was compared, with numbers",
  "evidence": {"selection_rule": "...", "...": "..."},
  "claims": [{"claim_id": "MCH-001-C1", "kind": "fact | risk | decision | recommendation",
              "statement": "...", "evidence": ["evidence.<key>"], "limitations": ["..."]}],
  "provenance": "from dclab_rnd.provenance.capture_provenance(...)"
}
```

Results that follow the five standard stages can live under `evidence/campaigns/<track>_v1/results/EXP-*.json`, where the evidence index, the critic gate and the SFT builder pick them up automatically.

## Conclusions

Measured on invented data only (the mall sales replica): the rules reach every planted cause in the question's own words
and in the template's, and few of them in other words; whether a model's reading closes that gap is the MCH records'.
