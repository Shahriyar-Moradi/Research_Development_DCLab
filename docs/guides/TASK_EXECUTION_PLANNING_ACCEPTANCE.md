# TP-03 — task execution planning

Status: complete under the owner's focused validation scope; independent review passed (2026-11-11).
Scope: TP-03 only. No dispatcher, task execution, persistence, recovery engine, product API or default rollout.

## Behavior and existing authority

`dclab_rnd.tasks.planner.plan_task` returns `(TaskExecutionPlan | None, report)` for one supplied leaf task.
The existing frozen `dclab_core.task_execution_plan.v1` contract and core graph/readiness/plan validators are reused.
No portable contract, schema, wheel configuration, existing tool handler, workflow guard or ML engine is changed.

The deterministic plan uses the adapter's exact registered operation: one `run_stage(project_id, stage)` call for
data, leakage, features, models or final, or one `export_notebook(project_id)` for the report. Final remains one
atomic operation containing training-only threshold selection and the protected holdout score. No `run_all`, extra
write, tool preview, guard invocation or read-tool call is used during planning.

For example, the ready `leakage` task produces one intent for the existing leakage stage. Its inputs bind the
current data evidence and execution context. Its expected output and acceptance checks come from the task graph.
The plan does not run an audit, claim the evidence exists, or mark the task completed.

A human gate or verification task yields an explicit `noop`: owner approval or independent evidence is still
required. A group, unsupported task, unready dependency, exhausted execution budget, unverified existing output or
failed/ambiguous prior attempt blocks. Prior failures must be reconciled by their existing owner. TP-05 owns later
recovery decisions; TP-03 does not retry effects or fabricate completion receipts.

## Inputs, validation and stale plans

Callers supply the source workflow and portable source plan, current project metadata, immutable TaskGraph, task ID,
current host observations, explicit registry capability snapshot and remaining execution budget. The observation
shape remains the one documented by TP-01C: current source/project identities, artifact hashes, source approval,
independently verified dependency receipts and, before final, unused holdout permission and an explicit use count.
The developer fixture's approvals and receipts are authored declarations, never authenticated runtime evidence.

Before planning, the adapter is recompiled against current metadata. All source references and atomic task fields
must match; a valid TP-02 grouping/dependency hierarchy is admitted. Set-like source/atomic field order is compared
canonically, matching the existing fingerprint rules. Current goal, dataset, solution, signoff, settings, source plan
or capability changes invalidate the old graph. All mandatory checks, output declarations and capability bindings
are copied from the deterministic task rather than regenerated by a model.

Plan arguments contain typed references only. Expected inputs bind required artifacts, the exact project/stage
constants, and a `planner_policy` hash over the versioned prompt and model output schema. The complete capability
fingerprint binds tool parameters, scope, effect, guarded move, permission and replay policy. The future execution
budget and zero-retry stop/escalation policy are part of the plan fingerprint.

`check_plan(...)` rechecks current source, permission, core plan invariants and remaining execution budget. It
resolves only fingerprinted allowlisted project/stage metadata and uses the real pure `Registry.check` for full
JSON Schema validation, including required/unknown arguments and types/enums. Source schemas containing reference
keys are refused by the existing adapter before validation, preventing remote schema resolution.

`resolve_action(plan, "call", ...)` repeats these checks and returns arguments only. A future TP-04 dispatcher must
refresh all host observations immediately before using it, then call the existing `Registry.call/acall` with the
current principal/scope/context. The registry guard and engine still own permissions, concurrency, approvals,
splits, leakage, actual input bytes and holdout consumption. A shape-ready plan is never authorization to run.

The first supported leaves are atomic, so there is exactly one action named `call`. The frozen contract supports
references to earlier declared outputs, but this slice does not invent multi-call leaves to exercise that feature.
Invalid, forward, self or undeclared output bindings are refused; future multi-action support must retain the
contract's ordering and validate resolved arguments at the guarded execution boundary.

## Optional model proposal and privacy

The new `task_planner` purpose is a separate harness role on the existing standard gateway tier. `enabled=False`
is the default. It is not wired into Home, the intern, a product route or a scheduler.

With explicit opt-in, the model sees only the typed baseline, its one allowed registry descriptor, the remaining
execution budget and code-owned failure codes. It cannot see rows, table previews, raw tool results, arbitrary
artifact values, free-form error messages or unrelated workspace data. Project metadata previews are ignored.
Unknown artifacts or private values in the supplied observation map are refused before a request. Only the exact
host project ID and stage constants can be resolved into tool arguments.

The model may propose bounded action references, execution budget and stop policy. It cannot rewrite source
decisions, expected inputs/outputs, checks or capabilities. One atomic primary effect and zero automatic retries
are mandatory. Invalid, stale, unavailable, refused, truncated, timed-out or overbudget responses retain the exact
deterministic plan. Exceptions contribute code-owned refusal reasons only, never provider or input text.

Model planning reuses TP-02's bounded one-attempt gateway request and POSIX deadline: 48,000 input bytes, 16,000
reply bytes, 1,800 requested reply tokens, 9,800 total output/thinking tokens, 30 seconds and a EUR 0.20 planning cap
by default. The OpenRouter reasoning allowance remains included in the gateway's full token check and reservation.
No repair, compatibility retry or shadow request is made. Unsupported thread/platform/active-alarm callers keep
the deterministic result. The future task's execution allowance is separate from the model-planning allowance;
the host must allocate both within its overall budget. Execution defaults to one tool call and at most 120 seconds
within the supplied execution allowance. These are caps, not measured runtime/cost estimates.

The gateway captures API thinking separately beside the answer, using the existing content-specific labels and
privacy policy. A dedicated test verifies the actual saved **API thinking summary** text and final answer. Model
reasoning fields are not requested in JSON and do not enter plans or role traces. The model output-schema hash is
bound in the plan policy input; the served model identity remains in its gateway exchange provenance.

## Review and remaining limits

Final independent review passed with no remaining correctness findings. Review found that tuple equality rejected a benign source-reference reorder despite an identical
canonical graph fingerprint. The fix compares source references and set-like atomic fields canonically. The new
regression reverses these orders and verifies the same valid plan fingerprint.

This remains a metadata-only developer API for the existing basic binary workflow. It trusts the host to provide
authentic approvals and verification evidence; it cannot authenticate them from a supplied JSON map. It does not
read actual bytes, estimate ML duration, consume approval, save task attempts or reconcile a crashed effect. The
future dispatcher must perform the authoritative live checks. Programme/multi-table/other-family mapping remains
blocked by the existing adapter. TP-04 is not started.
