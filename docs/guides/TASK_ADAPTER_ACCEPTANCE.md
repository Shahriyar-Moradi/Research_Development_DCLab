# TP-01D — deterministic binary workflow preview

Status: **complete**, verified on 2026-11-05. All TP-01D acceptance criteria and applicable package gates pass.
Scope: **TP-01D only**. Core remains **0.157.0** with unchanged contracts and schemas. TP-01E is not started.

## What was built

`dclab_rnd.tasks.adapter` converts one validated basic binary-classification SolutionWorkflow into an immutable
TaskGraph plus a JSON mapping report. It reads supplied metadata only. No new ML calculation, raw table access,
project save, tool call, human approval, scheduler or API/UI integration is added. Existing studio stages, the
registry and its guards remain execution owners.

The example uses the existing workflow builder and canonical project tool registry, not a private list of tool
schemas. The source plan is the real portable projection made by `core_adapter.plan_from_project` from a signed
saved solution. Mapping is deterministic and all nine mandatory source steps are accounted for.

## Python API and inspection

```python
from dclab_rnd.tasks import adapt_workflow, capability_snapshot

caps = capability_snapshot(registry, allowed_tools={"run_stage", "export_notebook"})
graph, report = adapt_workflow(workflow, source_plan, current_project_metadata, capabilities=caps)
```

The caller provides an existing Registry and explicit host policy for the snapshot. Registry membership is not
permission. Snapshot creation reads only name, schema, scope, effect, move and guard presence. It does not invoke
handlers or guards. Admitted write descriptors conservatively remain non-idempotent. Schemas with references are
blocked before JSON Schema validation, preventing implicit network or file resolution during planning.

The adapter accepts no store, runtime context or model client. It does not fetch a project or dataset. Metadata must
come from authenticated current host records; a model must never supply confirmation, capabilities or data hashes.

Run this from the repository root to inspect the supported example:

```bash
.venv/bin/python - <<'PY'
import json
from pathlib import Path
from dclab_core.contracts import SolutionPlan
from dclab_core.solution_workflow import solution_workflow
from dclab_rnd.agents import build_registry
from dclab_rnd.tasks import adapt_workflow, capability_snapshot

fixture = json.loads(Path("tests/fixtures/tasks/telco_metadata.json").read_text())
caps = capability_snapshot(build_registry(("project",)), allowed_tools={"run_stage", "export_notebook"})

    SolutionPlan.read(fixture["source_plan"]), fixture["project"], capabilities=caps)
print(report["status"], report["topological_order"])
print(graph.model_dump_json(indent=2))
PY
```

This is a developer inspection path using the Python callable. No product CLI, API or screen is introduced.

## Physical task tree and source mapping

```text
Binary classification solution
├── Preparation: data → leakage → features
├── Selection: models
├── Evaluation: human holdout gate → final
└── Reporting: export
```

The task dependency chain is `data → leakage → features → models → holdout → final → report`. Group nodes only
organize the tree and never execute. The report's topological_order lists the seven non-group tasks in dependency
order. No concurrency, dispatch or completion transition is implemented.

| Source step | Existing physical owner | Evidence reference |
|---|---|---|
| class_balance | data stage | data_record; protocol/target summary, additional measured fold proof required |
| lock_holdout | same data stage | data_record; holdout split and lineage |
| train_only_analysis | same data stage | data_record; training-only findings and lineage |
| leakage_audit | leakage stage | leakage_record |
| No abstract source step | features stage required by existing engine | features_record; training-validation check |
| choose_on_validation | models stage | models_record |
| holdout_gate | separate human gate, no capability | future owner approval evidence |
| threshold | final stage | final.evidence.task_assessment.threshold, selected on OOF training predictions |
| final_once | same final stage | evidence.holdout_metrics, holdout_primary_metric_ci, holdout_consumed, holdout_uses_in_this_project and RunRecord |
| report_limits | registered export_notebook, move capture | legacy report.md/notebook.ipynb, hashes and source final record |

One physical operation is one action task. There is no second lock_split tool, no separate threshold/final call,
no run_all shortcut, and no programme leaf decomposition. Every action binding comes from the current canonical
registry snapshot and its real parameter schema. The report preserves each source step's ID, block, kind, decision,
inputs/outputs, checks, rule, gate, finding references and columns.

Logical workflow artifacts are linked to existing owner records. Training rows, holdout and findings point to data
record evidence; they are not new persisted table files. class_balance and threshold declare no logical output, so
their source output mapping is empty. No artifact is asserted to exist merely because a node declares it.

## Source, input and approval identities

The graph binds the existing `studio.graph.solution_hash`, source SolutionPlan hash, source workflow hash, actual
derived ProblemCard hash and recorded dataset SHA-256. Project identity is bound separately through its graph ID
and fingerprinted project_context input. Revision changes do not overwrite an old graph.

An independent `solution` reference named execution_context identifies the host's solution execution configuration.
It is a metadata projection, not a second signed Solution object. Its digest is also a required input artifact for
every action/gate. The projection binds settings, effective pack (including draft fallback), categorical metadata,
column names and explicit sensitivity labels, feature programs, runtime plan, brief, exposure, adopted improvements,
proposal target/modifiers, and project name/goal. Its values are never copied into the graph/report. Changes to these
inputs change the structural identity; the original signed Solution hash retains its existing meaning.

Profiles, previews, category values, record bodies, file paths and credentials are not copied or queried. Profile
sensitivity must already be explicit; legacy classification that would require looking at previews is blocked.
Business goal context is represented by the derived ProblemCard identity; task text uses known template content.

The saved Solution must have current existing human signoff before any action binding is admitted. A proposed or
model-accepted plan cannot self-confirm an outcome. The existing signoff covers the saved Solution, not arbitrary
runtime plan policies, source workflows or new dataset bytes. If a saved runtime plan exists, its identity must
match the supplied source plan. Its hash is retained as another source reference. No new approval record is created.
`execution_authorized` is always false. A mapped graph still needs the existing core's current execution-approval,
input and receipt checks, then all original runtime guards immediately before any actual operation.

## Supported scope and fail-closed behavior

This first adapter supports the basic nine-step classification template, complete labels and the actual portable
projection of the signed studio solution. It compares adopted metric/feature/identifier/positive-label decisions.
Exact binary framing, complete-label and stratified-split declarations are also accepted. Extra unadopted solver
decisions are blocked; the adapter never pretends an advisory model-family decision changes the engine's families.
Effective kind is resolved by the existing owner. An imbalanced pack that selects rare_event is not silently
compiled as basic binary. Time/group/spatial splits, text/other kinds, attached/partial labels, related tables,
programme plans, solution maps and extra source steps need their own reviewed mappings and are blocked.

Invalid workflow contracts/content are refused before adaptation. Missing essential source identities or unsupported
workflow variants return `(None, blocked_report)` instead of invented hashes. When source identities are available,
missing capabilities, policy refusal or unconfirmed source decisions become explicit blocked tasks. The report's
status stays blocked and retains core validation issues.

A blocked diagnostic graph is not an admitted executable graph. In particular, the existing validator rejects a
dependency whose prerequisite is blocked. This package preserves that rule and reports it rather than weakening
core semantics or fabricating an executable replacement. Fix the missing source requirement and rebuild a fresh
proposal; do not treat its diagnostic ordering as permission to run.

Three verification limits are explicit in every report: data records do not persist per-fold class counts; OOF
threshold assessment can be absent; registered export makes legacy files, not canonical SolutionReport. Missing
proof blocks later verification. Neither export success nor an empty/noop plan is completion evidence. No repeated
final read is permitted to obtain a missing threshold assessment.

## Conditions that remain with the runtime

The adapter does not authenticate supplied dictionaries, verify actual table bytes or resolve live permissions.
It does not fetch ambient runner profile, code/prompt fingerprints, decision routing, model scope, stop/spend
switches, jobs, locks or current task attempts. The host must bind/recheck those at dispatch and reconcile unknown
attempt outcomes before any retry. Existing data_path/registry/graph/programme/engine owners remain authoritative
for actual storage, splits, fitting, selection, human approval and holdout consumption.

No task persistence backend is introduced. Metadata roundtrips use ordinary JSON independent of the file or
PostgreSQL project store. Backend regression results are reported only when actually executed.

`make core-wheel-check` passed on isolated Python **3.12.13** with core **0.157.0**, only its four declared direct
dependencies, and no unexpected distributions. The R&D host adapter is not copied into that wheel. All **262**
