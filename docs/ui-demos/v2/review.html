DCLab · Data science mode · design review

A calmer, more honest DCLab

I went through all 19 screens. The look is good: warm colours, clear type, room to breathe. The problems are about trust and focus. Pages mix sample data with your real project, every page repeats a big status box that disagrees with itself, and most screens have three orange buttons. Below: the ten problems, worst first, then the same pages redrawn.

What is wrong

Ten problems, worst first

Each one names the page where I saw it, why it hurts, and the fix.

  1. Sample data shown under your real project's name High

    Solution & data, Notebook, Leakage, Models

    The project picker says Churn. The page body shows Term-deposit calls, "V2 signed by Shahriyar, Sep 27", and the duration leak. That happened because the server read failed and the page fell back to its sample. A user can't tell invented numbers from real ones. DCLab promises honest numbers, so this breaks the core promise.

    Fix: never mix the two. If the real read fails, show a clear "can't reach the server" page. A sample only opens on request, with a "Sample" label on every screen.

  2. The status box takes 200 px on every page and contradicts itself High

    Every project page

    Workflow says all four steps are done. Solution says Data is current and Plan is "Next". Notebook shows Plan with a green tick and the word "Next" together. Evaluation says "No project is open", while its box shows Run done and Evidence "Ready to verify". Each page works out the state on its own, so they disagree.

    Fix: one thin project bar, one line high, built from one source. Show it only on project pages.

  3. Three orange buttons, and the main one is the wrong step High

    Home, Workflow

    Home has "Open Planner", "Build this chat as a project" and "Build project": three main buttons for one action. On Workflow the main button is "Run the data stage", but the page itself says training already ran. "Delete" sits in the same row as "Run".

    Fix: one main (orange) button per screen, and it is the real next step. Put Delete in a "⋯" menu.

  4. The reply box covers the assistant's answer High

    Home

    The agent's message ("I'm sorry, watching customers dry up…") shows faded behind the composer. The user can't read the question they are meant to answer.

    Fix: the composer sits below the messages, never on top of them. The list scrolls above it.

  5. The right panel is a raw event log Medium

    Home

    Eight rows like "set goal noted by the lead agent / by the agent". This is how the system records things, not what a person needs to see.

    Fix: show the problem card: Goal, Decision, Data, Open questions, Spend. Keep the log in Developer mode.

  6. Big-number cards hold words, and some never load Medium

    Workflow, Solution, Leakage, Models, Policy model, Domain packs

    "Shahriyar" in large type is an approval request, not a number. "duration", "extra_trees" and "caught" sit where numbers belong. Captions run to four lines. On Policy model and Domain packs, "…" never turns into a value.

    Fix: big cards hold numbers only, with a one-line caption. A request for your approval becomes a "Needs you" line. A card that fails says so ("—, couldn't load").

  7. One page, three names Medium

    Sidebar vs page titles

    "Workflow DAG" opens "Workflow". "Datasets & Schemas" opens "Solution & data". "Leakage & Drift" opens "Leakage & features". "Autonomous Agent" opens "Intern". "Interactive Notebo…" is cut off. The sidebar also has two headers on top of each other: NAVIGATION, then WORKSPACE.

    Fix: one name per page, the same in the sidebar, the top bar and the title. Use short names that fit: Workflow, Data, Notebook, Leakage, Models.

  8. Developer words in front of users Medium

    Intern, Validator, Workflow, Home

    "describe_data on project 411af13c0cd2", "`None` is still running", "Allowed. Allowed.", "task_planning_v3 tp06.gate.v2 PASS", "MODEL · QWEN/QWEN3.8-FLASH". Codes like WF-08 are the main label in the graph tiles.

    Fix: plain words first, codes second. For example "Tuning", with WF-08 small underneath. Raw ids belong in Developer mode only.

  9. Tables that wrap and highlight for no reason Low

    Compute & jobs, Models

    "2.0 / s" and "this / machine" break onto two lines. The Hardware column says "this machine" on every row. The first row is shaded, but nothing is selected.

    Fix: keep numbers and units on one line and right-aligned. Drop a column that is the same on every row. Shade a row only when it is selected.

  10. Charts and empty boxes don't explain themselves Low

    Leakage → Data look, Domain packs, Policy model

    The bars are orange or purple, but no legend says what purple means. Domain packs shows a table with headers and no rows. Policy model puts its error message in a narrow column on the left.

    Fix: one bar colour, a highlight with a legend ("above 40%"). Every empty box says what will appear there and how to get it.

Keep it fixed

Seven rules for every page

Most problems above come back if each page decides its own layout. These rules stop that. They could live at the top of look.css and be checked by make browser-test.

1 · Real or sample, never mixed

A sample always carries a "Sample" label. A failed read never falls back to a sample.

Like a bank: a demo account never shows your balance.

2 · One main button per screen

Only the true next step is orange. Destructive actions live in a menu.

Workflow: "Review evidence", not "Run the data stage".

3 · One name per page

The sidebar, top bar and title all use the same short word.

"Leakage" everywhere, not three names.

4 · Big cards hold numbers

One number, one-line caption. Words and requests go in a "Needs you" line.

"7 / 10 steps", not "Shahriyar".

5 · Plain words first

Codes, ids and model names go second, in small type or in Developer mode.

"Tuning", then WF-08 underneath.

6 · One project bar

One line, project pages only, worked out in one place, so every page agrees.

No page shows "Plan ✓ Next".

7 · Three states for every box

Loading, empty (what will appear and how), failed (what happened, what to do). Never a lone "…".

Domain packs: "No packs yet · Build a pack".
Order of work

How to apply it

  1. Let the other UI session finish and commit. It is editing the same files now (core.js, styles.css, ds.css, the views). Two writers on the same files overwrite each other.
  2. Trust first: rules 1 and 7. No sample under a real name, an honest server-down page, three states in every box. This is the most important change.
  3. Shared parts: rules 2, 4 and 6. One project bar and one button rule, in core.js and look.css. This fixes every page at once.
  4. Names: rule 3. Rename the sidebar entries and page titles to one short word each.
  5. Home. Composer below the messages, the problem card in the side panel, one build button.
  6. Page by page: rule 5, tables, charts. Each change checked with make browser-test at 1280 and 375 px.
