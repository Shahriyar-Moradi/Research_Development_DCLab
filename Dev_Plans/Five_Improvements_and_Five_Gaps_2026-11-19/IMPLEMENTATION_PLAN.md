# Implementation plan for Five Improvements and Five Gaps

Use the [review](PLAN.md) for impact and the [coding prompt](PROMPT.md) to assign one slice. The sequence below gives a modest coding model one concrete starting point. Tests use invented data, temporary paths and scripted services. Run the smallest relevant groups.

## I2 · Version-aware alert history

**First patch.** In `dclab_rnd/studio/service_template/serve_log.py`, trace `Log.monitor` into `_alerts`. In `tests/test_service_export.py` or its closest monitoring test, give two synthetic model versions one shared log directory. Emit the same alert text for the same window from each version, then repeat one report. The expected history has two rows; the repeated report must preserve its row's first-seen time.

**Implementation.** Use the same identity for historical rows and candidates: model ID, model version, canonical window and alert identity. Use the alert's stable code if the present schema has one; otherwise retain its existing exact label. Inspect the actual representation of day/week/batch windows and include the type if the window value can collide. Deduplicate within a single report too. Put lookup and append inside one process-safe critical section that spans all service workers sharing this log. An in-process mutex only protects one worker. Preserve current JSONL readers and log location. Older rows without an attributable version remain readable as historical entries and cannot suppress a new version's row.

**Verification.** Two different model IDs with matching version strings remain distinct. Two processes writing the same signal converge to one row. A repeated monitor request returns the same report and retains the original timestamp. Build an export in the relevant test to show the corrected template actually ships. Existing deployed service copies need a package update. Rollback can still read the expanded history.

## I1 · Export without a second holdout read

**Slice 1 — capture the winning fit.** Follow `dclab_rnd/studio/service.py::export` backwards from the recipe, estimator, calibrator, monitoring plan and live reference to the stage that creates the final evidence. Inventory every field currently derived from the frame or split, including NA-code policy, class labels, time-series bounds, thresholds and input types. At the original authorized final evaluation, capture the exact winning fitted state and approved serving metadata, using the aggregate test reference computed in that evaluation. Use only training-side data for training summaries. Preserve existing supported kinds and their refusal messages.

**Slice 2 — identify and publish it.** Stage a privacy-safe artifact in the storage abstraction. Bind the immutable artifact digest, format version, project, run ID, recipe/schema version, serving metadata digest and safe parity-fixture references to the final record. At approval bind the approved record to that exact candidate. Preserve the category-hashing behavior of `_strip`, monitoring-bin transformation and stable project log key. Keep serving secrets in the supported protected key channel. Confirm that salted/category transforms and corresponding key can be recovered for repeat export. Never package raw rows, category vocabularies containing private values or credentials. Load only verified host-created artifacts from trusted storage. Test the backend actually used for artifact bytes, including object-backed storage if supported.

**Slice 3 — export and recover.** Verify approval, artifact digest, schema and run binding before assembling the package in a temporary destination. Include copied runtime templates, serving metadata and the same fitted payload. Verify prediction parity on invented inputs using the repository's existing tolerance per task type. Atomically publish on success and preserve the previous export on failure. Legacy approved records lacking an artifact get an actionable “approved artifact unavailable” result. Show the affected run and what is missing. Any genuinely new final evaluation follows the existing governed workflow and its holdout-reuse rules; ordinary export never initiates it.

**Verification.** Use `tests/test_service_export.py` with an invented complete project. After the original final run, make preparation, fitting, scoring and held-out data access raise if invoked by export. Export twice and check the fitted identity, endpoint predictions, calibration and monitoring metadata. Corrupt or swap the artifact, revoke approval and inject a write failure; each must leave no newly published package. Check supported classification and regression paths and the existing unsupported-kind behavior. An incomplete capture must not be described as exportable. Rollback preserves the final record and keeps the verified-artifact path explicit.

## I3 · Make split coverage explicit before import

**Slice 1 — inventory.** In `dclab_rnd/connectors/hf.py`, trace `pick_file`, `pick_converted` and `fetch`, then the API and UI that invoke them. Resolve the revision to an immutable source commit before listing for a full import. Resolve a single configuration, split, coherent shard family and format in stable order. Preserve the explicit single-file train convention. Treat arbitrary same-extension files, ambiguous configurations, missing numbered shards and converted partial splits as ambiguous or partial coverage. Show known file count, total bytes if available, completeness and why a full import is unavailable. Keep inventories bound to the same resolved revision at download time.

**Slice 2 — choice and delivery.** New interactive callers explicitly select first-shard preview or full split. Show “1 of N files” and describe the preview as the first shard. Preserve the existing default and response fields for legacy API callers with additive coverage metadata. Fetch full input into temporary storage, enforce cumulative size during transfer or bounded staging, validate schema/column compatibility, concatenate in deterministic order, and publish one resulting table through the normal import API. Enforce disk and decoded-size limits during merging. If a size is unknown, display “unknown” and enforce limits while reading. Fail the full import on missing shards, schema mismatch or cancellation; allow explicit selection of preview afterward.

**Verification.** In `tests/test_connectors.py` use a fake provider with two shards; a class exists only in the second. Check preview count, full class coverage, one provenance entry per source shard with checksums, resolved revision and final row count. Test moving branches, partial conversions, mixed configs, duplicated filenames in different folders, unknown sizes, cumulative limit and mid-transfer failure. Confirm the choice and actual coverage appear at the normal import surface. Roll back the full-import option independently while keeping provenance readable.

## I4 · Honor Stop inside training

**Slice 1 — establish safe boundaries.** Trace `dclab_rnd/jobs/handlers.py::_stage_run` into the training stage and the loop that launches validation candidates. Trace `checkpoint`, worker ownership, progress and settlement. First guarantee a boundary between candidates. Add between-fold checkpoints only where scoring is already decomposed into independent units. A native fit that cannot yield finishes its current unit. Expose that boundary in the UI wording.

**Slice 2 — propagate cancellation.** Pass a host checkpoint through the affected call chain. Keep portable scientific code independent of the job system by using an optional callback if the loop belongs in core. Check before starting the next unit and before committing a winner. Preserve cancellation as a distinct exit. Guard against exception handlers interpreting it as a failed candidate and continuing. Check worker ownership when settling. Publish progress and completed evidence consistently; a partially evaluated candidate cannot become the selected model. Define the final once-only holdout read and its durable result write as a protected boundary. A stop before entry prevents it. A stop arriving after entry must allow an accurate committed outcome without a replay of the holdout.

**Verification.** Extend the relevant `tests/test_jobs.py` case using two synchronization events, one signaling candidate start, the other allowing completion after a stop request. Assert that candidate two never starts, the job settles once, polling reflects pending/settled state, and no partial winner exists. Test stop before start, repeated stop, a lost worker and stop on either side of final commit. No wall-clock timing assumptions. Direct callers with no cancellation callback retain their normal result.

## I5 · Prove what a backup can restore

**Slice 1 — make consistency explicit.** In `dclab_rnd/storage/backup.py`, trace `backup`, `_backup` and `restore`. Keep PostgreSQL's shared snapshot for dump and counts. Define distinct statuses for an archive captured, a proven consistent capture and a successful restore drill. Start with an offline or maintenance-mode capture that fences writers before the snapshot and holds the boundary until all relevant bytes are captured. Inventory API, workers, background jobs and external file writers. If the deployment cannot prove that fence or provide a common immutable generation, mark the capture unverified. Checksums alone cannot establish that files match the database snapshot.

**Slice 2 — verify and restore.** Add a versioned manifest with relative path, length and checksum for each archived file, database schema, capture mode, referenced artifacts and any missing entries. Hash the bytes actually archived. Where remote object versions are part of a workspace, record and verify those generations or explicitly report the unsupported scope. Validate referenced file identities against records where the storage interface exposes them. Preserve existing archive hash checks and safe extraction. Keep legacy manifests restorable with their original verification level.

**Slice 3 — run a drill.** Restore only to a disposable empty database and empty directory. Verify exact path set, content checksums, schema, counts and database-to-file identities. Return a machine-readable difference and unsuccessful drill status if any check fails. A failed drill leaves the live workspace untouched. Preserve enough diagnostic evidence for a retry with fresh empty targets.

**Verification.** Start with `tests/test_backup_retention.py`. Force a deterministic pause between dump and archive, then change, delete, replace with same-length bytes, or add a referenced file while a writer is active. Expect a blocked writer or an unverified capture. Mutate a restored file without changing counts and assert the drill detects it. Exercise one successful empty-target PostgreSQL restore using the repository's isolated test setup. A missing database service is a reported test dependency; it cannot count as a successful drill.
