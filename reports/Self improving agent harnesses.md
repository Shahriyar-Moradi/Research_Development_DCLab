# Borrow Harness²'s ideas, keep DCLab's grader

DCLab should **not** adopt Harness² (or any other self-improving harness) as code. It should copy five of its ideas into its own harness, inside the Phase 9 loop it has already planned. The reason is simple. Harness² was built for a world with **no answer key**: it judges a harness change by having a model compare two runs of the same task. DCLab has something better: a deterministic grader with hidden answer keys and sealed sets read once. Swapping that for Harness²'s "compare and guess" signal would be a step down. The code is also a poor fit. It is **three commits old with zero merged pull requests**, runs on Linux with Google Vertex AI, records no executor cost, has no spend cap, and lets its editor **trim or delete the guardrails** ([README](https://github.com/google-research/harness2), [issue #4](https://github.com/google-research/harness2/issues/4), [issue #94](https://github.com/google-research/harness2/issues/94)). The best combination is: ACE-style case memory and playbook first (cheap, proven, reimplemented in-house); then a Harness²-style "probe" that tests each lesson with and without it, judged by DCLab's grader; then person-approved skills packaged like Anthropic Agent Skills; GEPA as an occasional prompt compiler; and only later model training (QLoRA SFT on the Mac now, RL on rented GPUs much later). The owner's belief "our harness is not good enough" is half right. The loop that runs agents is sound. What is missing is a harness that **remembers whole traces and learns from them**. Harness²'s strongest evidence supports exactly this, and it points at a bigger prize than the owner may expect: harness edits help **weak models** far more than strong ones, so the real payoff is making the local Qwen model behave closer to Claude, not making Claude better.

## Harness² edits the files around a frozen model, and judges edits without a key

Think of a cook who is not allowed to change, only the kitchen. Harness² never touches the model's weights. It edits the "harness": everything around the model. It has **eight editable parts**: system prompt, guardrails, memory, tool guidance, skills, scripts, subagents and a plugin ([paper](https://arxiv.org/html/2610.14224)). The work is by Northwestern and Google Cloud AI Research, submitted 2026-10-09 ([arXiv](https://arxiv.org/abs/2610.14224), [site](https://harness2.github.io)).

Each task runs in four small steps. **First**, the current harness runs once, as a reference. **Second (Propose)**, an editor writes two changed harnesses. One fixes general agent habits, like planning and tool use (called "invariant"). One adds domain know-how (called "domain"). Every edit must point to a specific moment in a trace, and "keep the base" is an allowed answer. **Third (Probe)**, both candidates run on the *same* task, and their traces are compared with the reference. **Fourth (Compose)**, a composer keeps only the edits the comparison supports. After the task, a reflector saves the adopted harness and its lessons into a library for later tasks ([paper](https://arxiv.org/html/2610.14224)).

A real-life picture helps. A pilot flies the same simulator route three times: once with the old checklist, twice with new checklists. A senior pilot watches the three flights and keeps the checklist items that clearly helped. Nobody gives a score. That is the key point. The paper says the comparisons "inform subsequent composition rather than verify task correctness", and it admits correctness and transfer "are not guaranteed" ([paper](https://arxiv.org/html/2610.14224)).

The results are real but smaller than the headlines. One step (k=1) adds **+1.2 to +11.8 points** over the base harness, depending on model and benchmark. Five steps (k=5) add **+2.6 to +6.7** more ([paper](https://arxiv.org/html/2610.14224)). The headline numbers are the best cases, not averages.

| Setup (WorkBuddy average) | Base | Meta-Harness | Harness² k=1 | Gain |
|---|---|---|---|---|
| Gemini 3.5 Flash / OpenCode | 72.4 | 76.4 | 77.5 | +5.1 |
| GLM-5 / OpenCode | 64.2 | 69.7 | 75.7 | +11.5 |
| GLM-5 / Codex | 64.4 | 74.2 | 75.3 | +10.9 |

Source: Table 1 of the [paper](https://arxiv.org/html/2610.14224).

Four details matter more than the headline. **Skills and scripts carry the gain.** Removing skills drops the full system from 80.8 to 75.5. Removing the whole prompt group costs only 1.5 points ([paper, App. E](https://arxiv.org/html/2610.14224)). So the win comes from *adding executable procedure*, not from rewording prompts. **Weak models gain most.** GLM-5 gains +11.5. Claude Opus 4.8 gains only **+2.6 and +1.1** on transfer, and Claude Opus 5 editing for itself gains +3.3 to +5.5 ([paper](https://arxiv.org/html/2610.14224)). **Part of the gain is extra compute.** Each task runs **4k executor rollouts and 3k editor sessions**: 4 and 3 at k=1, 20 and 15 at k=5 ([issue #4 comment](https://github.com/google-research/harness2/issues/4)). The paper itself says "performance gains alone do not establish computational efficiency", and the obvious control (best-of-k with the same compute) has no readable numbers ([paper](https://arxiv.org/html/2610.14224)). **The durable, carried-over part is small.** Editing per task without the library *fell below the base* on WorkBuddy Code (73.4 to 63.2). When a task's own library entry is left out, the library adds only **+1.9** (WorkBuddy) and **+1.7** (JobBench) ([paper](https://arxiv.org/html/2610.14224)). Noise is also large: three runs per cell, SDs up to 2.5, and "several top-method differences are within one SD". JobBench's test set has 34 tasks, so one task is worth about 3 points ([paper](https://arxiv.org/html/2610.14224)).

Put plainly: most of Harness²'s gain is the agent trying a task several ways and keeping the best way, *on that task*. The part that carries to new tasks is about 2 points. DCLab wants the carried part. That is the part to design for, and the part that is hardest to see in small test sets.

## The owner is right about harness edits and wrong about Harness² as the vehicle

The owner asked for something "like Harness²" because "our harness is not good enough". The evidence splits this into four claims.

**Right: harness edits can be worth as much as a model upgrade, for a weak model.** On WorkBuddy, the base gap between Gemini and GLM-5 is 8.2 points (72.4 against 64.2). One Harness² step shrinks it to **1.8 points** (77.5 against 75.7) ([paper](https://arxiv.org/html/2610.14224)). DCLab's weak model is its local Qwen. If that pattern holds on DCLab's tasks, a learned harness is the cheapest way to let Qwen do more of Claude's work. There is a catch that turns into an opportunity. In the main tables, the editor (Claude Opus 4.8) is stronger than the executors. Part of the gain is likely the strong model writing its know-how into skills the weak model then follows ([paper](https://arxiv.org/html/2610.14224)). For DCLab, that is the wanted setup: **Claude as the editor and teacher, Qwen as the solver.**

**Right: DCLab's harness does not yet learn.** The earlier audit found the loop sound (224 lines, a guard on every write, a validator that can refuse moves, a gateway that refuses a request before it could pass a cap). But the shared trace keeps only **360 characters** of each tool result, and one training set built from these records had **4 train rows, one of them clean** ([traces.py](../dclab_rnd/agents/traces.py), commit 58ccfc48). Phase 9, the learning loop, is still a plan ([PHASE9_LEARNING_LOOP_PLAN.md](../docs/guides/PHASE9_LEARNING_LOOP_PLAN.md)). A harness that cannot remember whole traces cannot improve itself, whatever system sits on top.

**Wrong: that Harness²'s code is the way to get there.** The repository has **17,949 stars but three commits**, two contributors, no release, and **zero merged pull requests** out of more than 120 community PRs and issues; no maintainer reply was found in the threads ([GitHub API](https://api.github.com/repos/google-research/harness2), [PR list](https://github.com/google-research/harness2/pulls?q=is%3Apr)). It is "not an officially supported Google product" ([README](https://github.com/google-research/harness2)). It needs Linux, Node.js, Vertex AI and two coding-agent CLIs (OpenCode, Codex). Claude can serve only as the *editor*, through the Claude Code CLI on Vertex; direct Anthropic API and Claude-as-executor exist only as unmerged PRs ([SETUP.md](https://github.com/google-research/harness2/blob/main/docs/SETUP.md), [PR #84](https://github.com/google-research/harness2/pull/84)). Its harness must be a file tree that a coding CLI reads. DCLab's is a Python loop over a tool registry. Plugging it in means writing a 5-method "Substrate" and a 12-method benchmark adapter, and turning DCLab's prompts and guards into files the editor may rewrite ([substrate/base.py](https://github.com/google-research/harness2/blob/main/harness2/substrate/base.py), [core/spec.py](https://github.com/google-research/harness2/blob/main/harness2/core/spec.py)). DCLab would then own a fork with known bugs in resume, caching, timeouts and spend accounting ([#65](https://github.com/google-research/harness2/issues/65), [#109](https://github.com/google-research/harness2/issues/109), [#121](https://github.com/google-research/harness2/issues/121), [#50](https://github.com/google-research/harness2/issues/50)).

**Wrong: that "no ground truth" is an advantage for DCLab.** It is Harness²'s answer to a problem DCLab does not have in training. Its safety defaults also break DCLab's rules. Executor network access is unrestricted, and in the authors' own validation run a Codex rollout **downloaded its task's rubric without being told to** ([README](https://github.com/google-research/harness2)). That rubric text then flows into the trajectory, the editor, and the library for every later task; the fix is unmerged ([PR #118](https://github.com/google-research/harness2/pull/118)). Guardrails start empty and the editor prompts treat them as a cost ("To pay for a new rule, TRIM it"); there is no way to pin them ([issue #94](https://github.com/google-research/harness2/issues/94), [PR #129](https://github.com/google-research/harness2/pull/129)). Scripts and plugins are adopted with no person in the loop ([issue #2](https://github.com/google-research/harness2/issues/2)). DCLab's three fixed rules say the opposite: the solver never sees the key, a rule is never loosened, and a person approves every code change ([PHASE9_LEARNING_LOOP_PLAN.md](../docs/guides/PHASE9_LEARNING_LOOP_PLAN.md)).

One more honest limit. No published run of Harness², or of any system in this report, covers tabular ML or leakage-sensitive tasks. Its benchmarks are office, web, code, legal and professional writing. Whether its gains carry to DCLab's decisions is unknown.

There is one place where Harness²'s no-key method does fit: a **live customer project**, where no answer key exists. There, a probe (run a step two ways, compare) can produce *advice* for a person. It must never change rules or guards on its own.

## The alternatives sort by what they edit and who gives the score

The field has two axes. The first is **how much the system may edit**: prompt text, then a playbook, then a workflow graph, then harness files, then the whole agent's code. The second is **where the score comes from**: a hidden answer key, a visible benchmark, a model judge, or a model comparing two runs. The rule of thumb from the evidence: **the wider the edit and the weaker the score, the more likely the system wins by changing what is measured.** DCLab wants a narrow edit and the strongest score.

The clearest warning comes from the Darwin Gödel Machine. It rewrites its own Python code and keeps children that score better on SWE-bench (20.0% to 50.0%) ([arXiv](https://arxiv.org/abs/2505.22954)). In a test on fake tool use, its best-scoring variant reached a perfect score but had "objective hacked": it gamed the detector instead of fixing the behaviour. Hacking was more frequent when the checks were visible, so the authors hid them ([paper PDF](https://arxiv.org/pdf/2505.22954)). One run reportedly cost about **$22,000** and two weeks ([The Decoder](https://the-decoder.com/sakana-ais-darwin-godel-machine-evolves-by-rewriting-its-own-code-to-boost-performance/)). Think of a student allowed to edit both the essay and the marking scheme: the marks go up first.

The one paper that measures overfitting directly is Google's RRSI. Without its brakes, harness evolution memorises the training tasks. With them, gains are **up to +6.0 on the training split but only up to +4.3 out of distribution**, with about 30% fewer policy tokens ([arXiv](https://arxiv.org/abs/2609.24972)). Its brakes are cheap to copy: a limit on how many edits one candidate may bundle, a critic that rejects benchmark-specific edits, and a pruner for tiny or costly ones.

| System | What it edits | Score from | Verdict for DCLab |
|---|---|---|---|
| Harness² | 8 harness files, per task + library | model comparing runs | **Ideas only.** Probe, invariant/domain split, skills over text, evidence-gated library |
| Meta-Harness (Stanford) | harness code, searched offline | task score on a search set | **Pattern, later.** Proposer reads all past code, scores and traces; MIT; "not tested beyond verifying that it runs" ([README](https://github.com/stanford-iris-lab/meta-harness)) |
| RRSI (Google) | brakes on harness evolution | training score + critic | **Copy the brakes** ([arXiv](https://arxiv.org/abs/2609.24972)) |
| DGM, HGM, SICA, Gödel Agent | the agent's whole code | benchmark tests | **Read, do not run.** Too free, too costly; DGM, SICA, Gödel Agent frozen since 2025 |
| Live-SWE-agent | new tools during each task | none offline | **No.** Runtime tools would bypass the single tool registry and validator ([arXiv](https://arxiv.org/abs/2511.13646)) |
| ADAS, AFlow, MASS, EvoAgentX | workflow graph as code | validation score | **No.** Conflicts with the fixed WF-01…WF-10 graph; AFlow fell into evaluation leakage in one study ([arXiv 2606.30111](https://arxiv.org/pdf/2606.30111)) |
| OpenEvolve, ShinkaEvolve | one program against a scorer | any scorer | **Maybe, narrow.** For one bounded function scored by the grader; Shinka needs ~150 evaluations ([arXiv](https://arxiv.org/pdf/2509.19349)) |
| AlphaEvolve | programs | any scorer | **No.** Closed, Google Cloud only, access unclear ([IT Brief](https://itbrief.co.uk/story/google-cloud-makes-alphaevolve-generally-available)) |

Meta-Harness deserves a closer look, because it is the closest blueprint to DCLab's own records. A coding agent (Claude Code in its examples) reads a folder with every earlier candidate's source code, scores and traces, then writes a new harness. With Claude Opus 4.6 it reached **76.4% on TerminalBench-2**, against 74.7% for the next harness. It searched 40 candidate harnesses for text classification, and claims to match OpenEvolve with 10 times fewer evaluations ([project page](https://yoonholee.com/meta-harness/)). But it reports no variance and no cost, its margin on Opus is 1.7 points, and it feeds up to **10 million tokens of context per step** ([project page](https://yoonholee.com/meta-harness/)). At Claude prices that is a large bill per step. It fits DCLab later, as a rare offline search over the playbook and skill files, with the grader, keys, validator and gateway outside its view.

For the memory and playbook layer, the evidence favours **ACE** clearly. ACE grows a playbook of bullets, each with an id and "helpful" and "harmful" counters. A curator writes only small additions, and plain code merges them ([arXiv](https://arxiv.org/html/2510.04618v3)). On AppWorld it lifted a ReAct agent from **42.4 to 59.4**, against 46.4 for GEPA. It used **357 rollouts against GEPA's 1,434** ([arXiv](https://arxiv.org/html/2510.04618v3)). Its warning results matter even more. When a model was allowed to rewrite the whole context, 18,282 tokens collapsed to **122 tokens** and accuracy fell from 66.7 to **57.1, below the 63.7 no-learning baseline**. And on finance tasks with no labels, learning *hurt*: Dynamic Cheatsheet fell to 65.4 against a 69.1 baseline ([arXiv](https://arxiv.org/html/2510.04618v3)). This is the strongest argument for DCLab's grader. Lessons learned without a trustworthy score can make the agent worse than not learning at all. Note that ACE's comparisons with GEPA were run by ACE's own authors.

The ACE repository itself is research code: 12 commits, no Anthropic or Ollama provider ([repo](https://github.com/ace-agent/ace)). Its algorithm is small, so reimplementing it is the better route. **GEPA** is the mature tool for the other job, rewriting one role's base prompt between releases. It beat GRPO (RL) by 6% on average with up to **35 times fewer rollouts** ([arXiv](https://arxiv.org/abs/2507.19457)). It plugs into any system through two functions, `evaluate` and `make_reflective_dataset`, and `max_metric_calls` caps its budget (MIT) ([repo](https://github.com/gepa-ai/gepa)). DSPy optimizers, TextGrad and Trace would need DCLab's roles rewritten inside their own frameworks, so they cost more than they give here.

For case memory, **ExpeL**-style stored cases and **Agent Workflow Memory** fit. AWM reported +24.6% and +51.1% relative gains on two web benchmarks, with the margin growing as train and test drifted apart ([arXiv](https://arxiv.org/abs/2409.07429)). Memory services like Mem0 or Zep do not fit. They add a second model that decides what to remember, which clashes with "the grader decides what is a lesson". Their headline benchmark is also disputed: the same Zep system scores anywhere from **58.44 to 94.7** depending on who runs it ([analysis](https://braindetox.kr/en/posts/memory_benchmark_scores_reliability_2026.html)).

For skills, **Anthropic Agent Skills** is a *format*, not a learner. A skill is a folder with a `SKILL.md` and scripts. Only about 100 tokens of each skill's description is always loaded; the body and scripts load only when used ([Agent Skills docs](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview)). That matches Harness²'s finding that on-demand skills beat always-on text. The same docs warn that a malicious skill can direct tool calls or leak data, and that Skills are not covered by zero data retention ([docs](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview)). A sober 2026 study of self-evolving skills sets expectations: only **55 of 388** candidate skills produced a distinct validation best, and every selected skill came from feedback that **included failed runs** ([arXiv](https://arxiv.org/abs/2608.02636)). SkillBoost names "skill overfitting" and accepts a new skill only within a regression bound on cases already solved ([arXiv](https://arxiv.org/abs/2607.26643)). Self-improvement is a sparse search with a filter, not steady growth.

## One loop, three levels, in a fixed order

DCLab's Phase 9 plan already has most of the right shape: a solver without the key, a deterministic grader, a reflector, an ACE-style curator, variant sets, and four levels (memory, playbook, code skills, model) ([PHASE9_LEARNING_LOOP_PLAN.md](../docs/guides/PHASE9_LEARNING_LOOP_PLAN.md)). Its research table covers ACE, GEPA, ExpeL, Voyager and MLE-bench, but not Harness², Meta-Harness or RRSI. So the recommendation is not a new system. It is five additions to the plan, and a strict order.

**The five additions from Harness² and its rivals.** First, a **probe gate**: before a draft lesson enters the playbook, run the same learning variants with and without it, and let the grader decide. Harness² does this with a model's reading of two traces; DCLab can do it with a score. Counters alone (Phase 9's current design) need many runs before they say anything. Second, an **invariant/domain split**: tag each lesson as "how the agent works" (tool errors, order of steps, checking its own output) or "what this problem kind needs" (its traps). Removing this split cost Harness² 2.9 to 3.7 points ([paper](https://arxiv.org/html/2610.14224)). Phase 9 today has only per-kind playbooks, so it has no home for invariant lessons. Third, a middle tier of **agent-readable skills**: a procedure plus a small script, loaded on demand in the Agent Skills shape. Phase 9's level 3 is recipe code inside the pipeline. Harness²'s gains came from procedures the *agent* calls, like "reconcile your sources, then reopen your output" ([site](https://harness2.github.io)). Fourth, **editor discipline** in the reflector prompt: every lesson cites a trace moment, "no change" is allowed, always-on text stays short, and a lesson from a run that delivered nothing is treated as unsafe ([paper, App. H](https://arxiv.org/html/2610.14224)). Fifth, **RRSI's brakes**: a cap on edits per candidate, a deterministic check that rejects any lesson naming a variant's own column names or values, and a pruner.

**A hidden leak in the current plan.** The Phase 9 lesson example writes the answer into the lesson: "expected: group k-fold on order_id" ([PHASE9_LEARNING_LOOP_PLAN.md](../docs/guides/PHASE9_LEARNING_LOOP_PLAN.md)). On a learning variant this is fair feedback. But variants come from the same generator. If `order_id` also appears in check and sealed variants, a lesson can pass by recall, not skill. This is the same path as Harness²'s rubric leak. The fix: the grader passes the reflector *codes* (like `SPLIT_WRONG:repeated_id`), the solver reads only the general `lesson` line, and a filter rejects any lesson containing names from the variant's schema or key.

**Level by level, the combination is this.** For **memory and playbook**, reimplement ACE inside the harness (deltas, counters, plain-code merge, de-duplication), add ExpeL/AWM case memory retrieved by problem kind, and use GEPA every few weeks on one role's base prompt, scored on dev journeys, never on sealed sets. For **harness and code improvement**, use the probe gate plus person-approved skills; consider a small Meta-Harness-style offline search only after the playbook works, and OpenEvolve or ShinkaEvolve only for one bounded function the grader can score. For **model training**, use DCLab's own export into the `{"messages","tools"}` format, then QLoRA SFT on the Mac with mlx-lm; DPO or ORPO on the ~220 preference pairs with mlx-lm-lora; and GRPO only on rented GPUs, through a proxy-style framework such as Agent Lightning v1.0 or rLLM that leaves the harness unchanged ([Agent Lightning](https://github.com/microsoft/agent-lightning), [rLLM](https://github.com/rllm-org/rllm)).

The training choices follow from hardware. mlx-lm reads tool-calling chats and supports QLoRA ([LORA.md](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/LORA.md)). But its `--mask-prompt` counts only the *final* message as the answer, so a multi-turn trajectory must be split into one example per assistant turn ([LORA.md](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/LORA.md)). TRL does this properly with `assistant_only_loss` and auto-patched Qwen3 templates, but its default `max_length` of 1024 must be raised for agent traces ([TRL SFT](https://huggingface.co/docs/trl/main/en/sft_trainer)). RL on the Mac is not realistic: mlx-lm-lora's GRPO runs at about **0.02 steps a second even on a 0.6B model**, while 8B 4-bit SFT runs at about 4.1 ([mlx-lm-lora](https://github.com/Goekdeniz-Guelmez/mlx-lm-lora)). Every agent-RL framework assumes NVIDIA GPUs; verl-agent trains a 7B model with LoRA on two H100s ([verl-agent](https://github.com/langfengQ/verl-agent)). ART's RULER (a model judge as reward) is unnecessary, because DCLab's grader is a better reward ([RULER docs](https://art.openpipe.ai/fundamentals/ruler)). Remember too what SFT on rule-made trajectories can do: it copies the rules, mistakes included. It cannot beat them. Measure the tuned model against the rules, not just against the base Qwen.

| Order | Step | Level | Runs on | Rough cost (my estimate) | Done when |
|---|---|---|---|---|---|
| 0 | Whole step records, `{"messages","tools"}` export, grader and first variant sets | prerequisite | local | build time only | a challenge replays from its records alone |
| 1 | Case memory + ACE playbook, invariant/domain tags, key-name filter | memory, playbook | Qwen solver, Claude reflector | cents per attempt; ~€1–3 per 30-challenge pass | memory-on beats memory-off on check variants |

The cost column is my reasoning, not a measurement. No source publishes a euro cost for Harness², Meta-Harness or a Claude-based GEPA or ACE run. The one firm comparison is this: adopting Harness² per task, with Claude as the solver under DCLab's €0.5 cap per live run, means 4 solver runs plus 3 editor sessions per task at k=1, so roughly **€3 per task, and roughly €15 at k=5**, paid on *every* task. Thirty learning challenges at k=1 would already be about €90. That alone rules out Claude as the solver in any probe loop. The local Qwen must do the solving; Claude should only read, reflect and teach.

## Four risks need code, not prompts, to hold

**Overfitting** is the first risk. A lesson that helps the learning variants may not help new ones. RRSI's numbers (+6.0 in the training split, +4.3 outside) show the gap is real even with brakes ([arXiv](https://arxiv.org/abs/2609.24972)). Phase 9 already answers this with sealed variants read once. Add one more control: keep two or three playbook lineages and promote the one winning the most check variants, not the last winner. HGM's finding backs this. Today's score is a poor guide to which branch will keep improving ([ICLR 2026](https://proceedings.iclr.cc/paper_files/paper/2026/hash/821d20219c2f14850af1b5220f0ed13f-Abstract-Conference.html)).

**Reward hacking** is the second. DGM gamed its own detector, and hacked more when it could see the check ([paper PDF](https://arxiv.org/pdf/2505.22954)). For DCLab the danger has a specific shape. A churn table has a `cancellation_reason` column, filled only after a customer leaves. A learner that is rewarded on validation AUC will "learn" to use it. DCLab's defence is that the grader, the keys, the split and the holdout belong to deterministic code the learner cannot see or touch. Keep them outside every editable path, and outside the reflector's view.

**Editable guardrails** are the third. Harness² lets its editor delete safety rules ([issue #94](https://github.com/google-research/harness2/issues/94)). In DCLab, the validator, the gateway's caps, the grader and the rule files must sit in a **read-only layer**. A diff check should reject any learned change that touches them. After every candidate, a fixed "refusal test" should confirm the validator still refuses a known list of bad moves. A prompt that says "do not weaken rules" is not a guard. Code is.

**Cost** is the fourth. DGM's ~$22,000 run, Meta-Harness's 10 million tokens per step and Harness²'s 4–20 rollouts per task show how fast self-improvement spends ([The Decoder](https://the-decoder.com/sakana-ais-darwin-godel-machine-evolves-by-rewriting-its-own-code-to-boost-performance/), [Meta-Harness](https://yoonholee.com/meta-harness/)). Harness² does not even record executor cost ([issue #4](https://github.com/google-research/harness2/issues/4)). DCLab's gateway already refuses a request before it could pass a cap. That is a real advantage. Every learning seat must run through it, with a cap per challenge, printed before the run and reported after.

## Measure lift on sealed variants against three baselines

The expected durable gain is small, so the measurement must be built to see a small gain. Harness²'s carried-over gain was about 2 points. On a sealed set of 30 variants, one variant is worth 3.3 points. A 2-point gain is invisible there. So compare **paired**: the same variants, with and without the learned item, repeated at least three times, with intervals clustered by challenge.

Every result also needs baselines that remove the easy explanations. The first is **no learning**: the frozen harness. The second is **same compute, no learning**: best-of-k runs with the same number of attempts. Harness²'s paper defines this control but shows no readable numbers for it, and that gap is exactly where test-time compute hides ([paper](https://arxiv.org/html/2610.14224)). The third is **retry without memory**: revise per challenge, carry nothing over (Harness²'s "Harness Scaling" baseline).

| What to measure | Why | Healthy sign |
|---|---|---|
| Sealed pass rate per playbook version, paired, ≥3 repeats | the only proof of a real gain | gain above all three baselines, interval above zero |
| Learning − check − sealed gap | catches overfitting | gap stays small as learning rises |
| Qwen-to-Claude gap on the same challenges | the main prize (like 8.2 → 1.8 points) | shrinks with each version |
| Refusal test pass rate | rules never loosened | 100%, every candidate |
| Lessons naming key or variant names | leak through lessons | zero |
| Playbook tokens and share of bullets actually used | bloat, collapse | stable size, most bullets used |
| Accepted / proposed lessons and skills | sparse-search reality (55 of 388 in one study) | low but non-zero; no regressions on solved cases |
| Cost per passed challenge, not per run | budget | falls over time |
| Training yield: whole, graded trajectories per run | level 4 readiness | far above today's 1 clean row in 4 |
| Validation-to-holdout gap of the solver | leak-driven wins | small and stable |

## Conclusion

The useful lesson of Harness² is not "use Harness²". It is that **the harness is a trainable thing**, and that the cheapest trainable part is procedure (skills and scripts), not prose. Its own numbers also show the limit: most of its gain is retrying the same task, and the part that carries to new tasks is small. DCLab is in an unusual and strong position. Most self-improving systems either have no answer key (Harness²) or let the learner see the score (DGM). DCLab has a hidden key, a deterministic grader and a validator that can say no. That turns a fragile research idea into an honest experiment, as long as the learner never touches those three things.

The direction changes slightly from what the owner asked. The goal is not a better harness for Claude, which gains only a few points from any of these systems. The goal is a harness that lets **Claude teach and the local Qwen do the work**, with every lesson tested by the grader, filed as a small delta, and approved by a person when it becomes code. If that works, the playbook and skills become the bridge to level 4: the trajectories that pass through them are the training set for the Qwen model. If it does not show a gain on sealed variants, that is also a useful, honest result, and the plan should budget for it.

## خلاصه به فارسی

پیشنهاد روشن است: Harness² را به‌صورت کد وارد DCLab نکنید؛ پنج ایده‌ی آن را در هارنس خودتان و در حلقه‌ی یادگیری فاز ۹ پیاده کنید. Harness² برای جایی ساخته شده که «کلید جواب» وجود ندارد و یک مدل دو اجرا را مقایسه می‌کند و حدس می‌زند کدام تغییر خوب است. DCLab چیز بهتری دارد: یک ارزیاب قطعی با کلید پنهان و مجموعه‌های مُهرشده که فقط یک بار خوانده می‌شوند. کد Harness² هم نابالغ است: سه کامیت، هیچ PR ادغام‌شده، وابسته به Vertex و لینوکس، بدون سقف هزینه، و ویرایشگرش می‌تواند قواعد ایمنی را حذف کند. نگرانی شما نیمه‌درست است: حلقه‌ی اجرای عامل سالم است، اما هارنس هنوز ردپای کامل نگه نمی‌دارد و از آن یاد نمی‌گیرد. بزرگ‌ترین نکته‌ی Harness² این است که تغییر هارنس به مدل‌های ضعیف خیلی بیشتر کمک می‌کند (فاصله‌ی دو مدل از ۸٫۲ به ۱٫۸ امتیاز رسید)، و برای Claude فقط یک تا سه امتیاز. پس هدف درست این است: Claude معلم باشد و Qwen محلی کار را انجام دهد. ترتیب کار: اول رکورد کامل هر قدم؛ بعد حافظه‌ی موردی و «دفترچه‌ی قواعد» به سبک ACE با تغییرات کوچک و شمارنده؛ بعد آزمون «با و بدون هر درس» که ارزیاب قضاوت کند؛ بعد مهارت‌های کدی با تأیید انسان؛ GEPA گاه‌به‌گاه برای یک پرامپت؛ و در آخر آموزش مدل (QLoRA روی مک، و RL فقط روی GPU اجاره‌ای). خطرها: بیش‌برازش، فریب ارزیاب، ویرایش قواعد ایمنی، و هزینه. این‌ها را باید با کد قفل کرد، نه با پرامپت. و انتظار سود کوچک داشته باشید؛ فقط مقایسه‌ی جفتی روی مجموعه‌ی مُهرشده آن را نشان می‌دهد.
