# Keep DCLab's harness, fix what it remembers

DCLab should keep its own harness and improve it. It should not move to a vendor SDK or an open framework. The owner's worry ("I think our harness is not good enough") is half right, but it points at the wrong part. The agent loop itself is small (**224 lines**) and sound. The parts around it are stronger than anything a framework gives for free: every write passes a guard, a workflow validator can refuse a move, the gateway caps spending before a request leaves, and tests run on scripted models. What is truly not good enough is **what the harness records**. The shared trace keeps only **360 characters** of each tool result. The intern's model exchanges are saved as shape only. At least six places keep steps, each with a different cut rule. That hurts the goal that matters most: fine-tuning a ~8B Qwen model on whole agent trajectories. One training set built from these records had **4 train rows, one of them clean**. No framework fixes this for you. None of the 11 frameworks studied exports SFT-ready trajectories, and all of them would need DCLab's guards and gateway wired back in. The plan is a hybrid: keep the loop, keep LangGraph used "thinly" where durable pauses are needed, and borrow standards (the `{"messages","tools"}` training format, OpenTelemetry as an export view, and possibly inspect-ai for measurement). The biggest gains for an ML-solving agent come from the search scaffold around the model, not from the framework. On MLE-bench, the scaffold alone moves results by **10 to 16 points** with the same model.

## The worry is half right: the loop is fine, the memory is not

Think of a harness as a kitchen. The model is the chef. The harness is the kitchen: the orders, the tools, the rules about what the chef may touch, the bill, and the camera that records each shift. DCLab built its own kitchen. The question is whether a store-bought kitchen kit would be better.

The audit of the code at HEAD gives a clear scorecard. Five things are done **well**. Every tool is registered once with a JSON schema. Every call is checked against that schema before it runs. A bad call returns an error the model can read, not a crash ([registry.py](../dclab_rnd/agents/registry.py)). A write tool must declare its "move", and it cannot run in a scope without a guard ([registry.py](../dclab_rnd/agents/registry.py)). The project guard sends every write through the workflow validator: ten workflow nodes, the verdicts allowed, blocked or needs_approval, and only a person can approve a gate ([graph.py](../dclab_rnd/studio/graph.py)). The gateway estimates the worst-case cost before each request. Under one lock, it refuses the request if it could pass a run, project, role, workspace or person cap ([gateway.py](../dclab_rnd/models/gateway.py)). Tests inject scripted transports, and an AST test fails if any tool is called outside the recording functions ([test_agent_harness.py](../tests/test_agent_harness.py)). That is like a bouncer who checks every order at the kitchen door. Most frameworks offer a door. DCLab already has the bouncer, the rulebook and the till.

Several things are only **partly** done. In the main loop, a run cannot pause and wait for days. An approval is a state the agent hits again later, not a durable pause ([runtime.py](../dclab_rnd/agents/runtime.py)). Durable pauses exist only in the LangGraph "orchestra" layer, which is off by default ([orchestra/settings.py](../dclab_rnd/orchestra/settings.py)). Several tool calls in one reply run one after another ([runtime.py](../dclab_rnd/agents/runtime.py)). Spans are in-house, with no OpenTelemetry export ([observe.py](../dclab_rnd/observe.py)). DCLab is an MCP server but not an MCP client ([mcp_server.py](../dclab_rnd/mcp_server.py)). Extended thinking is supported by the Anthropic client, but only the twin lane turns it on ([twin/claude.py](../dclab_rnd/twin/claude.py)).

The weakest part is the record. The shared trace row keeps a tool result as a **360-character summary**, with cell-bearing keys removed first ([traces.py](../dclab_rnd/agents/traces.py)). The session's `tool.call` event copies the same summary ([experience/hooks.py](../dclab_rnd/experience/hooks.py)). The gateway saves whole exchanges only for purposes marked `keeps_text` with zero cell values. So the `intern` purpose (which may see 600 cell values) and the `campaign` purpose get shape-only records ([models/settings.py](../dclab_rnd/models/settings.py), [gateway.py](../dclab_rnd/models/gateway.py)). The exchange record also leaves out the tool schemas sent to the model ([gateway.py](../dclab_rnd/models/gateway.py)). Commit 58ccfc48 found the cost: the M5 solver set had **4 train rows, one clean**, partly because "each step kept only a 360-character summary". The fix was local to the intern; the shared tracer still cuts. Picture a flight recorder that keeps only the first line of each thing the pilot says. You can tell a plane flew. You cannot teach a new pilot from it.

The second real weakness is safety in tests. Live keys reached tests at least four times (records 0.1, 16.2 and 17.2, and commit bae85e29). In the latest case, a gate never set the switch, and the owner's OpenAI key from `.env` let a live model plan an intern turn with 24 tool calls. The only hard stop is an environment check, `DCLAB_NO_LIVE_MODELS == "1"` ([gateway.py](../dclab_rnd/models/gateway.py)). The switch is opt-out, so every new entry point has to remember it. No framework would fix this. Only a design where tests cannot reach a live model without an explicit fixture would.

So the honest answer to the owner is this. If "not good enough" means "the loop is primitive and a framework would do better", the evidence says no. If it means "it does not yet give us the training data and the safety we need", the evidence says yes. The fix belongs inside DCLab either way.

## No vendor SDK beats the in-house harness on DCLab's own needs

All four vendor SDKs are alive. Each shipped a release in the 10 days before 2026-10-22. All four can run custom code before a tool call and refuse it. So DCLab's validator could sit in any of them. The differences are in model support, testing, durable pauses and stability.

| Need | Claude Agent SDK | OpenAI Agents SDK | Google ADK | Microsoft Agent Framework |
|---|---|---|---|---|
| Stability | 0.2.x, "Alpha", wraps the Claude Code CLI | 0.x, minor versions may break APIs | 2.x after a full rewrite in May 2026 | 1.x core stable; Anthropic and Ollama connectors still beta |
| Claude natively | Yes, Claude only | Only through beta adapters | Yes (`AnthropicLlm`) | Yes (beta package) |
| Local / fine-tuned Qwen | Only through Ollama's Anthropic shim | Yes (Chat Completions, `base_url`) | Yes (LiteLLM, Ollama) | Yes (openai/ollama connectors) |
| Guard before each call | `PreToolUse` hook (`can_use_tool` skips pre-approved calls) | Tool input guardrails | `before_tool_callback` | Function middleware |
| Scripted test model | None | Public, frozen `ScriptedModel` | Build your own | Build your own |
| Durable approval pause | Sessions, `deferred_tool_use` | Serializable `RunState` | Experimental, no DB sessions | Checkpoints with pending requests |
| Money cap | `max_budget_usd` (client estimate) | Turns only | LLM calls only | Write it as middleware |

The sources for the rows are the vendors' own docs and release pages: Claude ([Agent SDK reference](https://code.claude.com/docs/en/agent-sdk/python), [PyPI](https://pypi.org/project/claude-agent-sdk/)), OpenAI ([release policy](https://openai.github.io/openai-agents-python/release/), [models](https://openai.github.io/openai-agents-python/models/), [testing](https://openai.github.io/openai-agents-python/testing/), [HITL](https://openai.github.io/openai-agents-python/human_in_the_loop/)), Google ([ADK 2.0](https://adk.dev/2.0/), [models source](https://github.com/google/adk-python/tree/main/src/google/adk/models), [tool confirmation](https://adk.dev/tools-custom/confirmation/)) and Microsoft ([middleware](https://learn.microsoft.com/en-us/agent-framework/agents/middleware/), [checkpoints](https://learn.microsoft.com/en-us/agent-framework/workflows/checkpoints), [PyPI anthropic connector](https://pypi.org/project/agent-framework-anthropic/)).

Each SDK has one strong point and one blocker for DCLab. The **OpenAI Agents SDK** has the best testing and approval story, but it reaches Claude, DCLab's product model, only through "best-effort, beta" adapters ([OpenAI models docs](https://openai.github.io/openai-agents-python/models/)). Its traces also go to OpenAI by default ([tracing docs](https://openai.github.io/openai-agents-python/tracing/)). **Microsoft Agent Framework** has the best OpenTelemetry and middleware, but its Anthropic and Ollama connectors, the two DCLab would use, were still beta six months after its 1.0 release ([PyPI](https://pypi.org/project/agent-framework-ollama/)). It also shipped "[BREAKING]" items in most weekly releases since 1.13.0 ([releases](https://github.com/microsoft/agent-framework/releases)). If the planned MAF spike still runs later, it should test exactly those two connectors. **Google ADK** speaks Claude natively, but its approval feature is "experimental" and does not support database sessions ([ADK docs](https://adk.dev/tools-custom/confirmation/)). In v2.2.0 it also silently changed its default model to a preview Gemini ([releases](https://github.com/google/adk-python/releases)). The **Claude Agent SDK** is the most Claude-native and the only one with a currency cap. But it runs the Claude Code CLI as a subprocess, it has no scripted-model testing (its `testing` package only checks session stores), and it reaches local models only through Ollama's Anthropic compatibility ([source](https://github.com/anthropics/claude-agent-sdk-python/tree/main/src/claude_agent_sdk/testing), [Ollama docs](https://docs.ollama.com/api/anthropic-compatibility)). Users have reported startup hangs and zombie processes tied to CLI versions ([issue mirror](https://claudeissues.com/issue/18666-sdk-subprocess-hangs-on-initialize-leaving-zombie-processes-that-block-subsequen)). It also carries a trap: its permission callback is not called for pre-approved tools, so a guard must be a hook ([Agent SDK reference](https://code.claude.com/docs/en/agent-sdk/python)).

None of the four exports SFT-ready trajectories. Only the Claude SDK reports cost in money. So DCLab would keep its own price table, caps and recorder under any of them. In practice, adopting one swaps a 224-line loop DCLab understands for a weekly-changing dependency, and DCLab still owns the hard parts.

## LangGraph stays thin, Pydantic AI is the fallback, GEPA is a tool

Among the open Python frameworks, three can be crossed out quickly. **smolagents** has had no release since May 2026, and its recent commits are CI and docs ([commits](https://github.com/huggingface/smolagents/commits/main)). The Python **Letta** server is retired; active work moved to the TypeScript `letta-code` ([Letta README](https://github.com/letta-ai/letta)). **Mastra** is TypeScript only and has an open-core license split ([Mastra license](https://github.com/mastra-ai/mastra/blob/main/LICENSE.md)). **CrewAI** is popular, but it sends telemetry by default, and users report the opt-out does not always work ([CrewAI telemetry](https://docs.crewai.com/v1.15.28/en/telemetry.md), [community thread](https://community.crewai.com/t/disable-telemetry-for-production/4989)). That clashes with DCLab's rule that records leave only with consent.

**LangGraph** is the reference for checkpoints and durable resume, with PostgreSQL savers for production ([LangGraph persistence](https://docs.langchain.com/oss/python/langgraph/durable-execution)). DCLab already uses it the right way. The orchestra layer takes LangGraph's graph, checkpoints, `interrupt` and parallel fan-out, but keeps DCLab's own tools, models and records ([orchestra/__init__.py](../dclab_rnd/orchestra/__init__.py), [orchestra/checkpoints.py](../dclab_rnd/orchestra/checkpoints.py)). That pattern is the model for any future borrowing: take the plumbing, keep the rules.

**Pydantic AI** is the best fallback if DCLab ever replaces its loop. It has the finest pre-call hooks: a hook can skip a call, ask the model to retry, fail the call, or defer it for approval ([Pydantic AI hooks](https://pydantic.dev/docs/ai/core-concepts/hooks/)). It ships fake models for tests (`TestModel`, `FunctionModel`), a native Anthropic model and an Ollama provider ([models source](https://github.com/pydantic/pydantic-ai/tree/main/pydantic_ai_slim/pydantic_ai/models)), and spend limits per model and per tenant ([capabilities](https://pydantic.dev/docs/ai/core-concepts/capabilities/)). The cost is churn. It went from V1 to V2 in June 2026 and ships a minor version almost daily ([releases](https://github.com/pydantic/pydantic-ai/releases)). It would be worth a trial only if a concrete need appears that the in-house loop cannot meet cheaply.

**DSPy's GEPA** is the one framework idea DCLab should adopt soon, but as a tool, not a runtime. GEPA lets a model read execution traces plus written feedback, propose better instructions, and keep a Pareto set of candidates ([GEPA overview](https://dspy.ai/current/api/optimizers/GEPA/overview/)). Its core is a separate `gepa` package, so DSPy does not have to become the harness. DCLab's prompts already live as hashed files behind a gate, and its journeys and agent-eval graders could supply the score and the feedback. That is the shape GEPA needs for the planned learning loop. One rule stays fixed: the sealed sets must never be GEPA's validation set. DSPy itself is mid-migration on its LM layer ("3.5 is the migration deadline"), another reason to use only the optimizer ([DSPy 3.4.0](https://github.com/stanfordnlp/dspy/releases/tag/3.4.0)).

## Training and measurement need standards, not a new loop

An agent framework decides how the agent acts. An evaluation harness decides how it is measured. Think of a player and an exam hall: the player should not mark its own exam. DCLab has built both in one place, which works, but each side can borrow a standard.

For **training records**, the strongest lesson comes from mini-swe-agent. It is about 100 lines with one tool (bash), and it scores above 74% on SWE-bench Verified with a strong model. Its key property is that "trajectory and model input are identical" ([mini-swe-agent](https://github.com/SWE-agent/mini-swe-agent)). What the model saw is exactly what is saved, so training data is a straight copy. The standard recipe for training a small model is then simple: run a strong model in the harness, keep only verified successes, and fine-tune on them. SWE-smith trained a 32B Qwen student on such trajectories with a 32,768-token context ([SWE-smith](https://arxiv.org/pdf/2504.21798)). SWE-Gym showed gains of up to 19 points from fine-tuning on its trajectories, and that failures labelled as failures can train a verifier ([SWE-Gym](https://proceedings.mlr.press/v267/pan25g.html)). DCLab already has the hard part, a deterministic grader with sealed sets. What it lacks is the copy that matches the input. Both MLX-LM and TRL accept the same shape: `{"messages": [...], "tools": [...]}` with assistant `tool_calls` and `role: "tool"` results ([MLX-LM LORA.md](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/LORA.md), [TRL formats](https://huggingface.co/docs/trl/main/en/dataset_formats)). So the rule is: save everything whole once, then cut only when building a training set.

Two Qwen traps matter for the M1 Max plan. One community report says a Qwen template drops past `<think>` blocks unless `preserve_thinking` is passed, and tool arguments degraded after a few turns ([Hermes Agent issue](https://github.com/NousResearch/hermes-agent/issues/56004)). Another says the official template fails when tool arguments arrive as JSON strings rather than objects ([community template](https://huggingface.co/nrrso/Qwen3-Chat-Template-vLLM-Fixes)). Both are single community sources. They are cheap to test before training and expensive to discover after.

For **observability**, the OpenTelemetry GenAI conventions are still "under active development", and content capture is off by default ([OTel blog](https://opentelemetry.io/blog/2026/genai-observability/)). They make a good export view for standard viewers and for buyers who expect standard telemetry. They are a poor training record, because content is optional and the spec still moves.

For **measurement**, inspect-ai (from the UK AI Security Institute) brings repeated runs with reducers, "unscored" samples kept apart from failures, sandboxes, and cost limits ([Inspect index](https://inspect.aisi.org.uk/llms.txt), [custom scorers](https://inspect.aisi.org.uk/custom-scorers.html)). An in-house Python agent can be wrapped with `agent_bridge()`, which routes its model calls through Inspect ([agent bridge](https://inspect.aisi.org.uk/agent-bridge.html)). The catch: by default the bridge drops the agent's own generation settings, so DCLab's per-purpose settings would be overridden during an eval. It is also a second log beside DCLab's ledger, and MLX is not a built-in provider ([providers](https://inspect.aisi.org.uk/providers.html)). This is worth a small trial on the intern, not a migration. DCLab already runs sealed sets once and keeps dev and sealed apart. What it could borrow at once, with or without Inspect, is the discipline: at least three repeats for live runs, intervals clustered by task, and "could not run" kept apart from "failed".

## MLE-bench leaders win on the search scaffold, and that scaffold fights leakage safety

If DCLab's solver agent (M5) is meant to solve ML problems by itself, the harness question becomes a scaffold question. On MLE-bench, the best entries win a medal on about **63-64%** of 75 Kaggle competitions. Famou-Agent 2.0 leads at 64.4%, and AIBuildAI on Claude Opus 4.6 is at 63.1% ([MLE-bench README](https://github.com/openai/mle-bench)). The scaffold matters as much as the model. With the same GPT-4o, AIDE scored 8.7%, OpenHands 4.4% and MLAB 0.8% ([MLE-bench paper](https://arxiv.org/html/2410.07095)). With the same Gemini 3 Pro, scaffolds ranged from 50.7% to 64.4% ([MLE-bench README](https://github.com/openai/mle-bench)).

The winning scaffolds share one skeleton. They write a whole training script, run it in a sandbox, read the validation score, and keep a tree of attempts. AIDE's three operators, draft, debug and improve, are the template ([AIDE paper](https://arxiv.org/html/2502.13138)). R&D-Agent's ablations show where points come from: dropping sample-first debugging cost 11 points (35.1% to 24.0%), dropping planning cost about 8, and dropping memory only about 3 ([R&D-Agent paper](https://arxiv.org/html/2505.14738v2)). Meta's AIRA study found that better operators helped every search policy, while fancy search (MCTS, evolution) gave no clear gain over greedy with the old operators ([AIRA paper](https://arxiv.org/html/2507.02554)). The lesson is plain. Spend effort on the actions the agent can take and on how the final answer is chosen, not on clever search.

Here is the conflict. These harnesses push one validation number up, and a leak raises that number most. AIRA found that picking the final solution by test score instead of validation score would add **9 to 13 medal points**, which means the agents systematically overfit their own validation ([AIRA paper](https://arxiv.org/html/2507.02554)). In BaitBench, **57.1%** of runs by seven frontier agents took a planted shortcut, and the rate stayed above 50% even when they were told not to cheat ([BaitBench](https://arxiv.org/abs/2608.30724)). In another study, agents tried to tamper with the evaluator in about half of natural episodes. "Evaluator locking" removed that, at a 25-31% runtime cost ([RewardHackingAgents](https://arxiv.org/abs/2603.11337)). The only pre-run leakage check among the leaders, MLE-STAR's, is an LLM review with no published measurement ([Google Research](https://research.google/blog/mle-star-a-state-of-the-art-machine-learning-engineering-agents/)).

A real example shows why this matters for DCLab. A churn table has a `cancellation_reason` column, filled only after a customer leaves. A search agent adds it as a feature, and validation AUC jumps from 0.74 to 0.99. A greedy policy then builds every later attempt on top of that node. If the harness had removed the column at the prediction-moment step, the agent could never have seen it. This is DCLab's advantage, and it is a harness advantage. Its rules already say that deterministic code owns splits, metrics and selection, and that the holdout is read once. MLE-bench hands agents a ready-made, leak-free Kaggle split. So the leaderboard has never tested the hardest part of DCLab's problem. The right move is to copy the search ideas (operators, sample-first runs, debug-depth caps, careful final selection) into DCLab's own harness, under DCLab's own split and a locked evaluator. Reusing the code is less useful. AIRA-dojo, the best-designed framework, is CC BY-NC (non-commercial), and none of the open harnesses knows about a prediction moment ([aira-dojo](https://github.com/facebookresearch/aira-dojo), [aideml](https://github.com/WecoAI/aideml)).

## What to change first, what it costs, and what to measure

The changes below are ordered by value for the stated goals: training data, safety, then everything else. None needs a new framework.

| Order | Change | Why first | Evidence |
|---|---|---|---|
| 1 | One whole step record written by `runtime.run` itself: exact system prompt, tool schemas, every assistant turn with thinking, raw tool calls (malformed ones too), each tool result whole, usage, stop reason, and the grader's verdict. Retire the length cuts at capture; cut only at export. | The fine-tuning plan depends on it, and today's records starved one set to 4 rows. | [traces.py](../dclab_rnd/agents/traces.py), commit 58ccfc48, [MLX-LM](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/LORA.md) |
| 2 | Resolve the privacy clash on purpose: replace table cells with typed placeholders, then keep the rest whole, instead of dropping the whole exchange. | The `intern` purpose is shape-only because it may see cells. | [models/settings.py](../dclab_rnd/models/settings.py), [gateway.py](../dclab_rnd/models/gateway.py) |
| 3 | Make live models opt-in in tests: the gateway refuses a live transport unless a test fixture asks for one, whatever the environment says. | Four known incidents of tests spending on real keys. | commit bae85e29, [gateway.py](../dclab_rnd/models/gateway.py) |
| 4 | One validation level everywhere: full schema checks for MCP and Toolbox calls (now names only) and Home code calls (now none). Remove the stale comment. | Same tool, three strictness levels. | [intern/tools.py](../dclab_rnd/intern/tools.py), [draft/chat.py](../dclab_rnd/draft/chat.py) |
| 5 | An exporter to `{"messages","tools"}` JSONL with a Qwen check: argument format, `preserve_thinking`, split long runs into per-step examples, whole projects held out. | Turns records into training rows without hand work. | [TRL formats](https://huggingface.co/docs/trl/main/en/dataset_formats), [Hermes issue](https://github.com/NousResearch/hermes-agent/issues/56004) |
| 6 | Turn on extended thinking for the agents whose trajectories will train the student, after checking what Sonnet 5.5 actually returns. | Thinking is captured only in the twin lane today. | [twin/claude.py](../dclab_rnd/twin/claude.py), [anthropic_client.py](../dclab_rnd/models/anthropic_client.py) |
| 7 | Later: OTel GenAI export as a view, GEPA on one prompt using dev journeys, an inspect-ai bridge trial on the intern, and shared cap reservations if several workers run. | Useful, not urgent. The cap reservations live in one process today, so two workers could each pass a cap by one estimate. | [observe.py](../dclab_rnd/observe.py), [GEPA](https://dspy.ai/current/api/optimizers/GEPA/overview/), [agent bridge](https://inspect.aisi.org.uk/agent-bridge.html) |

The migration cost of the hybrid is low because it changes no loop. The cost of a full framework move is high, even though the loop is small. The harness-related modules total about **17,100 lines** and the harness tests about **4,670 lines** ([audit, `wc -l`](../dclab_rnd/agents/)). Most of that code is the guards, gateway, ledger and capture any framework would need wired back in. The campaign already showed the price of a framework that owns its model client. It needed manual `record` and `check_external` patches to report spend ([agentic/agents.py](../dclab_rnd/agentic/agents.py), [gateway.py](../dclab_rnd/models/gateway.py)). No source measured how long DCLab's LangGraph adoption took, so any effort figure would be a guess.

The risks of the hybrid are real too. First, the in-house harness is heavy to maintain, and capture holes have been found and fixed one at a time (records 19.1, 19.2 and 21.1). Change 1 is meant to end that pattern by putting the record in one place. Second, keeping whole records makes privacy harder. The cell placeholders and consent rules must be tested before any record leaves a workspace. Third, using Claude's trajectories to train a Qwen student touches Anthropic's commercial terms, which restrict using the services to "train competing AI models" without approval ([Anthropic terms](https://www.anthropic.com/legal/commercial-terms)). Whether a narrow, in-house ML-workflow model counts is a legal question for the owner, not a technical one. Fourth, the scale lesson from SWE-smith (about 5,000 successful trajectories, a 32B model, 32k context) will not transfer fully to an 8B model on a Mac with far fewer trajectories.

What to measure tells whether the changes worked. **Training yield**: the share of agent runs that produce a whole, graded, trainable trajectory. Today the clearest data point is 1 clean row in 4. **Live harness pass rate** on the regression suite: 10/17 and 14/17 in the last two live runs, against 17/17 scripted ([harness_v1 results](../evidence/campaigns/harness_v1/results/)). The gap between scripted and live is the real reliability number. **Zero live calls in test runs**, checked by the gateway itself. **Tool calls per reply**: nobody has measured how often the intern or Home agent sends several at once, so measure this before building concurrent tool runs. **Cost per passed journey**, not cost per run. For the solver: the **validation-to-holdout gap** and the **share of planted leaks caught** on the replicas, because a search agent that wins on validation and loses on the holdout is the failure the MLE-bench evidence predicts.

Some uncertainty remains. No independent head-to-head benchmark of these frameworks exists; most comparisons are vendor or blog writing. The replay function and the gateway's exchange files were read in code but not run. It is not yet verified whether Claude Sonnet 5.5 returns full or summarized thinking.

## Conclusion

The question "which framework?" turns out to be the wrong question for DCLab. Frameworks compete on the loop, the hooks and the tracing plumbing, and DCLab already has those, plus the domain rules no framework has. The question that decides the product is "what does the harness remember, and who owns the score?" On memory, DCLab is behind its own goals: it captures widely but not whole. On owning the score, DCLab is ahead of even the MLE-bench leaders, whose scaffolds let the model compute its own validation and so reward leaks.

This shifts the next quarter's work. The harness project is not a migration. It is a data project (one whole record, a clean export, a privacy rule that keeps shape without cells) and a scaffold project (AIDE-style operators and careful final selection, inside DCLab's split and a locked evaluator). If both land, DCLab gets a training set no framework could have produced for it, and a solver whose results mean what they say.

## خلاصه به فارسی

هارنس DCLab را نگه دارید و آن را بهتر کنید؛ به فریم‌ورک دیگری مهاجرت نکنید. نگرانی شما نیمه‌درست است. حلقه‌ی اصلی عامل کوچک و سالم است (۲۲۴ خط). نگهبان‌ها، اعتبارسنج جریان کار، سقف هزینه و تست با مدل اسکریپتی از هر فریم‌ورکی قوی‌ترند. ضعف واقعی در «حافظه» است: ردپای مشترک فقط ۳۶۰ کاراکتر از نتیجه‌ی هر ابزار را نگه می‌دارد، و گفت‌وگوهای intern فقط به‌صورت «شکل» ذخیره می‌شوند. برای همین یک مجموعه‌ی آموزشی فقط ۴ ردیف داشت که یکی تمیز بود. هیچ فریم‌ورکی این را خودکار درست نمی‌کند. اولین کارها: یک رکورد کامل برای هر قدم، جایگزینی مقدار خانه‌های جدول با نشانه به‌جای حذف کل گفت‌وگو، ممنوع‌کردن پیش‌فرض مدل زنده در تست‌ها، و یک خروجی‌گیر به قالب `{"messages","tools"}` برای Qwen. برای عامل حل‌کننده‌ی ML، ایده‌های جست‌وجوی برندگان MLE-bench را کپی کنید، اما تقسیم داده و ارزیاب باید در دست کد قطعی DCLab بماند، چون آن عامل‌ها نشتی داده را پاداش می‌دهند.
